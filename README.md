# AI 数字员工（客服 / 行政）— 产品设计文档集

> **一个嵌在 OA 与客服工作台里的 AI 数字员工：先答得准（知识 + 订单可查），再办得成（按风险分级承接改地址、退款等写操作）。**

这是一套从 0→1 的完整产品设计文档，共 15 篇，覆盖战略定位、用户价值、MVP 范围与验证闸门、指标体系、技术选型、评测体系、权限安全，以及 8 个模块的详细设计。

## 几个关键设计选择

| 主题 | 选择 | 出处 |
|---|---|---|
| 产品形态 | 嵌入既有工作台，**不做独立入口**（独立入口必然在第二月归零） | 00-§1.2 条件五 |
| 写操作 | 三闸门：模型建议 → 后端规则校验 → 人工确认；AI **只推进到「可办结」**，不等于独立完成 | 29-§2.1；30-§5.2 |
| 链路 | 六节点：多模态输入 → 意图识别 → Query 改写 → 任务路由 → ReAct 生成 → 合规校验 | 30-§3.1 |
| 可评测性 | 每个 Badcase 必须能定位到六个节点之一，否则不允许上线迭代 | 00-§1.2 条件四；26 |
| 知识管理 | QA 库（高频标准问答）与 RAG 库（长文档）**分开维护**，避免新旧口径混答 | 00-§1.2 条件三 |
| 主力模型 | 百炼千问系分级用模；DeepSeek 为异构备选（受合规豁免前置约束） | 25-D1/D2 |
| 向量库 | PG16 + pgvector（HNSW）+ FTS 关键词双路 | 25-D6 |
| 文档解析 | 三级链 MinerU → 百度 OCR → VLM，带解析版本化元数据 | 25-D7 |

## 关于这套文档的证据口径

这套文档刻意保留了**决策时点的不确定性**，而不是事后包装成"一切尽在掌握"：

- 标注体系：`事实` / `推断` / `假设（待验证）` / `未核验` 四级，逐条标注来源。
- **痛点 P1–P7 全部标为假设**——未做一手用户访谈，不虚构用户原话。
- 所有阈值与目标值均为决策时点的**暂定值**，不是行业基准；上线后的实测结果集中在 00-附录 A（标注样本量与测量方式），并明确**不参与任何决策推导**（避免用结果倒推理由）。
- 各篇开头的「变更记录」保留了决策被修正的过程（例如 33 篇登记了一处引用勘误）。
